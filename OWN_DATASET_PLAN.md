# OWN_DATASET_PLAN.md — собственный корпус траекторий

## 1. Зачем свой датасет (научное обоснование, а не объём)

В публичном корпусе каждая связка «агент × модель» прогоняла каждую задачу один раз.
Поэтому пара «успех — провал» внутри задачи — это всегда **две разные модели**, и нельзя
отделить «агент работал плохо» от «это более слабая модель». Литература (Beyond Resolution
Rates, arXiv 2604.02547) показывает, что поведение агента определяется в основном LLM, то есть
угроза реальная.

Свой корпус устраняет её конструктивно: **одна модель, одна задача, несколько повторов**.
Пары «успех — провал» при одинаковых задаче, модели, каркасе и конфигурации различаются только
тем, как прошёл конкретный прогон. Это самая строгая проверка того, что структура траектории
несёт сигнал о достоверности выполнения. Публичные данные такой проверки дать не могут.

Побочные результаты:
- **Воспроизводимость.** Доля решённых и распределения признаков в своих прогонах сравниваются
  с прогоном той же модели на лидерборде. Совпадение подтверждает, что конвейер корректен.
- **Разброс между повторами.** Насколько исход одной модели на одной задаче случаен. Это
  отдельный измеримый факт: верхняя граница предсказуемости по структуре.

## 2. Решения, фиксируемые до первого запуска

| Параметр | Решение | Почему |
|---|---|---|
| Каркас | mini-SWE-agent, та же версия и тот же конфиг bash-only, что у прогонов v2.0.0 в корпусе | Траектории разбираются существующим адаптером и сравнимы с корпусом |
| Модель | Одна дешёвая модель средней силы из тех, что уже есть в корпусе. Кандидаты: `glm-4.6` (решено 56%, медиана 41 шаг), `devstral-small-2512` (62%, 62 шага), `minimax-m2` (63%, 62 шага). Выбор — по измеренной стоимости прогона (этап 1) | При доле решённых около 50–60% пар «успех — провал» больше всего. Наличие модели в корпусе даёт проверку воспроизводимости |
| Температура | Фиксированная, ненулевая, одинаковая во всех прогонах; значение записывается | При температуре 0 повторы почти одинаковы и пар не будет. Значение в конфиге лидерборда проверить и записать отдельно |
| Задачи | Из SWE-bench Verified, доля решённых по 16 связкам корпуса от 0.4 до 0.6 (36 задач) — основной пул; при нехватке расширить до 0.25–0.75 (117 задач). Отбор детерминированный, seed 42 | Задачи средней сложности дают смешанные исходы |
| Повторы | Пилот — 3, основной сбор — 3, для подмножества 5 | См. раздел 4 |
| Лимиты | Лимит шагов и стоимости — как в конфиге лидерборда | Иначе обрывы по лимиту не сравнимы с корпусом |
| Метка | Официальный инструментарий оценки SWE-bench (`swebench.harness.run_evaluation`) в Docker, поле `resolved` | Та же метка, что в корпусе |
| Что логируется | Полная траектория mini-SWE-agent (`.traj.json`), `report.json` оценки, конфиг, версия mini-SWE-agent, имя модели и провайдера, температура, токены и стоимость, время, digest Docker-образа, номер повтора | Воспроизводимость и анализ стоимости |

Все решения записываются в `own_data/PROTOCOL.md` **до** запуска пилота и не меняются в ходе
сбора. Если изменение неизбежно — новая версия протокола, а старые прогоны помечаются.

## 3. Почему не подписка Claude и не Opus

**mini-SWE-agent через подписку — нельзя.** Подписка Pro/Max не выдаёт API-ключ. Её OAuth
предназначен для обычного индивидуального использования Claude Code и приложений Anthropic.
Извлечение токена подписки для стороннего каркаса запрещено условиями.

**Claude Code как агент через подписку — технически можно, но не для основного корпуса.**
1. Это другой каркас: свои инструменты (Read, Edit, Bash), свой промпт. Траектории не сравнимы
   с корпусом mini-SWE-agent и требуют отдельного адаптера.
2. Сотни автоматических прогонов выходят за рамки «обычного индивидуального использования»,
   на которые рассчитаны лимиты подписки. Это риск ограничений аккаунта. Перед любым
   пакетным запуском читать актуальную политику на support.claude.com.
3. Лимиты подписки общие с чатом и Claude Code. Opus расходует их быстрее всего.

**Opus не нужен и по научной причине.** Сильная модель решает задачи средней сложности почти
всегда, провалов мало, пар «успех — провал» мало. Для этого дизайна средняя модель лучше
дорогой.

**Допустимое использование подписки:** небольшой отдельный набор (десятки прогонов) Claude Code
на тех же задачах как проверка переноса на другой каркас. Только после основного корпуса,
только в объёме обычной ручной работы, с повторной проверкой политики.

## 4. Ожидаемый выход пар

Если модель решает задачу с вероятностью p, вероятность получить оба исхода за n повторов
равна 1 − pⁿ − (1 − p)ⁿ.

| p | 3 повтора | 5 повторов |
|---|---|---|
| 0.5 | 0.75 | 0.94 |
| 0.3 или 0.7 | 0.63 | 0.83 |
| 0.1 или 0.9 | 0.27 | 0.41 |

Основной сбор 100 задач × 3 повтора = 300 прогонов даст порядка 50–70 задач со смешанным
исходом внутри одной модели. Пилот 5 × 3 = 15 прогонов должен дать хотя бы одну такую задачу.

## 5. Инфраструктура

Агенту и оценке нужен **Docker** с образами SWE-bench (по одному на задачу, порядка
гигабайта и больше). Colab и Kaggle Docker не поддерживают — для этого корпуса они не подходят.
Ноутбук с двумя ядрами подходит только для одиночного smoke-теста.

| Вариант | Плюсы | Минусы |
|---|---|---|
| Локально, Linux или WSL2 | бесплатно | медленно, диск, образы большие |
| Арендованная VM (4–8 vCPU, 100+ ГБ диска) | надёжно, параллельно | несколько долларов на пилот; машину выключать сразу после сбора |
| GitHub Actions в публичном репозитории | Docker есть, бесплатные минуты для публичных репозиториев | лимиты диска и времени на задание; допустимость такого использования проверить в условиях GitHub |

Решение принимается на этапе 1 по результату smoke-теста.

## 6. Схема данных

Те же таблицы, что в демо (`runs.parquet`, `steps.parquet`), той же схемы и тем же кодом
разметки фаз и признаков. Дополнительные колонки в `runs`:

| Колонка | Смысл |
|---|---|
| `source` | `leaderboard` или `own` |
| `repeat_idx` | номер повтора, с 0 |
| `temperature` | температура генерации |
| `provider` | провайдер API |
| `cost_usd`, `tokens_in`, `tokens_out` | стоимость и токены прогона |
| `wall_time_s` | длительность прогона |
| `config_sha256` | хеш конфига mini-SWE-agent |
| `image_digest` | digest Docker-образа задачи |
| `protocol_version` | версия `own_data/PROTOCOL.md` |

Структура каталогов:

```
own_data/
  PROTOCOL.md
  tasks_pilot.json, tasks_main.json
  raw/<run_id>/<task_id>.traj.json      # неизменяемо после записи
  eval/<run_id>/<task_id>/report.json
  runs_own.parquet, steps_own.parquet
  SHA256SUMS
  LOG.md                                # журнал запусков, сбоев, расходов
```

Сырые траектории не изменяются после записи. Всё производное пересобирается скриптом.

## 7. Этапы

### Этап 0. Подготовка (без вызовов API)
1. Найти конфиг bash-only, которым получены прогоны v2.0.0 корпуса: лимиты, температура,
   промпт. Записать в `PROTOCOL.md`.
2. Измерить стоимость: в сырых траекториях mini-SWE-agent есть статистика модели
   (стоимость и число вызовов, если поле присутствует). По 355 локальным сырым траекториям
   вывести медиану и 90-й перцентиль стоимости прогона для каждой модели-кандидата.
3. Отобрать задачи пилота: 5 задач из пула 0.4–0.6, разные репозитории, медиана длины
   по корпусу не выше 60 шагов.
4. Записать критерии пилота (раздел 8) в `PROTOCOL.md`.

### Этап 1. Smoke-тест — одна траектория
1. Установить mini-SWE-agent закреплённой версии, Docker, инструментарий SWE-bench.
2. Один прогон выбранной модели на одной задаче пилота.
3. Оценка патча, получение `resolved`.
4. Разбор траектории существующим адаптером, разметка фаз, признаки, строка в
   `runs_own.parquet` той же схемы, что в демо.
5. `score_trajectory` из демо-ноутбука выдаёт риск для этой траектории.

Критерий: цепочка «запуск → траектория → метка → признаки → риск» проходит без ручных правок.

### Этап 2. Пилот — 5 задач × 3 повтора = 15 прогонов
Это первые примеры для руководителя.

### Этап 3. Решение go / no-go
По критериям раздела 8. Если критерий не выполнен — сначала устранить причину, затем повторить
пилот. Масштабировать неработающий конвейер нельзя.

### Этап 4. Основной сбор
100 задач × 3 повтора; для 30 задач со смешанным исходом — ещё 2 повтора. Запуск партиями
по 20–30 прогонов с проверкой расхода после каждой.

### Этап 5. Анализ
- AUROC внутри пар «одна задача, одна модель» для `M_len` и `M_struct+len`.
- Сравнение с внутризадачным AUROC на корпусе лидерборда (там пары из разных моделей).
- Перенос: модель, обученная на корпусе лидерборда, применяется к своим траекториям без
  дообучения.
- Воспроизводимость: доля решённых и распределения ключевых признаков против прогона той же
  модели в корпусе.

## 8. Критерии пилота (фиксируются до запуска)

| Критерий | Порог |
|---|---|
| Прогоны, завершившиеся без технических сбоев | не меньше 14 из 15 |
| Траектории, разобранные адаптером без ошибок | 15 из 15 |
| Метка получена | 15 из 15 |
| Медианная стоимость прогона | не выше бюджета, заданного на этапе 0 |
| Задачи со смешанным исходом | хотя бы 1 из 5 |
| Доля решённых | в пределах ±0.2 от доли решённых той же моделью на этих задачах в корпусе |
| Медиана длины траектории | в пределах ±30% от корпуса для той же модели |

Последние два критерия ловят расхождение конфигурации: другой лимит, другую температуру,
другую версию каркаса.

## 9. Риски

| Риск | Что делаем |
|---|---|
| Повторы почти одинаковы | Проверить температуру на пилоте; если исходы во всех тройках совпадают, повысить температуру в новой версии протокола |
| Провайдер API меняет модель под тем же именем | Записывать точное имя и дату; весь основной сбор — за короткий период |
| Образ Docker не собирается или тесты нестабильны | Задачу исключить с записью в `LOG.md`; заменить следующей из пула |
| Расход выше оценки | Остановка партии при превышении; бюджет задаётся явным флагом скрипта |
| Изменение конфига в ходе сбора | Запрещено протоколом; хеш конфига в каждой строке |
