## 5. Ключ API

- Ключ берётся из переменной окружения **`ZAI_API_KEY`** и никогда не пишется в файлы: ни в конфиг, ни в журналы,
  ни в репозиторий.
- Ключ **не передаётся через `model_kwargs`**: mini-swe-agent сохраняет конфиг целиком в `info.config` каждой
  траектории — так ключ попал в публичный корпус. Его читает litellm из окружения процесса.
- Перед записью траектории и любых производных файлов — проверка, что значение ключа в них не встречается; при
  совпадении прогон останавливается, файл не сохраняется.

### 11.1. Критерий доли решённых → анализ после сбора

Коридор доли решённых (раздел 3, [0.114; 0.514]) **больше не условие допуска**. Пилот вышел из коридора (0.80), а
диагностика показала, что корпусная метка — один прогон при температуре 1.0, а часть корпусных меток задач
psf/requests искажена сбоем сети. Вместо критерия после сбора выполняется заранее заданный анализ воспроизводимости:

- пары: по каждой задаче `tasks_main.json` — **первый повтор** (`repeat_idx = 0`; у задач пилота — прогон `pilot_r0`)
  против прогона glm-4.6 той же задачи в корпусе (`20251201_mini-v1.17.1_glm-4.6`);
- корпусная метка **перепроверяется нашей оценкой**: патч оценки лидерборда (`logs/<задача>/patch.diff` в публичном
  бакете; проверка на ключи перед сохранением) оценивается тем же swebench 4.1.0, с теми же флагами и образами и с
  пробой сети (11.3). Если у корпусного прогона нет патча или он пуст, его метка — 0;
- таблица 2×2 «корпус (наша оценка) × наш первый повтор», **точный тест McNemar** (двусторонний биномиальный тест
  по несовпавшим парам, p = 0.5). Сообщаются таблица, число несовпавших пар каждого вида, p-значение; дополнительно —
  та же таблица с меткой лидерборда вместо перепроверенной. Результат описательный: от него не зависит, используются
  ли данные.

### 11.2. Задачи psf/requests исключены

В тестах этих задач до 58 PASS_TO_PASS и до 8 FAIL_TO_PASS обращаются к внешнему `http://httpbin.org/`
(`audit/requests_network_tests.json`). Метка зависит от состояния чужого сервиса в момент оценки. В логах лидерборда
сбой сети есть у 31 из 128 прогонов (4 задачи из 8), и все упавшие в них тесты — сетевые. Наша переоценка 30
затронутых прогонов с resolved = 0 даёт: 19 меток 0 → 1, 7 не определены (все на 2317), 4 остаются 0
(`LABEL_AUDIT_REQUESTS.md`). Доля решённых на 1724, 1766 и 1921 с 0.50 становится 0.875–0.94: в коридор эти задачи
попали из-за сбоя. У нас 2026-10-28 при любом патче падают тесты, которые ходят на https к httpbin.org (сервис
сменил сертификат, а старый requests в образе задачи его не принимает) или на `redirect-to` с внешним адресом
(теперь 403). Поэтому задачи репозитория psf/requests в пул не входят. 3 прогона пилота на
`psf__requests-1766` остаются в файлах с `protocol_version = 1.1`, но **в данные основного сбора не входят**.

### 11.3. Проба сети перед каждой оценкой — заменена (11.6, п. 4)

Решением автора 2026-10-28 проба заменена валидацией эталонными патчами (11.7); ниже — как она была устроена.
Скрипт сохранён, по умолчанию выключен. Перед оценкой каждого прогона `infra/eval_run.sh` запускает `infra/httpbin_probe.sh <задача>`: `GET
http://httpbin.org/get` (тайм-аут 15 с) из контейнера образа этой задачи с сетью Docker по умолчанию — так harness
запускает контейнеры оценки; используется python 3 базового conda образа. Если ответ не 200, оценка
**откладывается**: повторная проба через 10 мин, всего до 6 проб. Если все 6 не прошли, `eval_run.sh` завершается с
кодом 5, ничего не оценив; прогон остаётся без метки, оценка повторяется позже. Каждая проба (время UTC, статус)
пишется в `eval/<run_id>/httpbin_probe.log`. Ограничение: проба проверяет только http-доступ к httpbin.org. Сбой
https, как с сертификатом 2026-10-28, изменение ответов отдельных адресов (`redirect-to` с внешним адресом — 403
с 2026-10-28) и недоступность других внешних хостов она не ловит.

### 11.6. Вопросы автору до запуска — закрыт (решения автора 2026-10-28)

1. **65 вместо 70 задач.** Правило даёт 65 (≥ 60, расширение не срабатывает). **Решение: пул — все 65 задач, правило
   не меняется.**
2. **Ограничение «30 задач» для доп. повторов.** **Решение: +2 повтора задачам со смешанным исходом, не больше 30
   задач; приоритет — порядок задач в `tasks_main.json`.** Прогноз 11.5 с ограничением: сценарий 0.4 — 235 прогонов
   (26 задач, ограничение не срабатывает), 0.63 и 0.75 — 243 прогона (30 задач, 60 доп.).
3. **Бюджет.** **Решение: основной сбор останавливается при суммарном расходе $35 без пилота; расход проверяется
   после каждого прогона.** Расход — сумма `instance_cost` всех прогонов протокола 1.2, включая неудачные попытки из
   `raw_failed/`, если их траектория сохранилась. Проверка после прогона, поэтому перерасход — не больше одного прогона
   (≤ $3, `cost_limit`).
4. **Https в пробе.** **Решение: проба сети (11.3) заменяется валидацией окружения эталонными патчами (11.7).**
   `infra/eval_run.sh` пробу больше не запускает (включается только `OWN_HTTPBIN_PROBE=1`).

### 11.7. Этап V — валидация окружения эталонными патчами (без вызовов LLM API)

- До основного сбора эталонный патч SWE-bench Verified каждой из 65 задач оценивается нашей оценкой (swebench 4.1.0,
  те же флаги и образы, `--predictions_path gold`, `run_id gold_pre`); `report.json` сохраняются
  (`eval/gold_pre/<задача>/`).
- Задача, где эталон не `resolved`, **исключается из пула**. Для каждой — упавшие тесты и похоже ли это на внешнюю
  зависимость (сеть, сертификат, пакет, образ). Отчёт — `GOLD_VALIDATION.md`.
- **Если исключено больше 5 задач — остановка** до решения автора. Иначе — основной сбор.
- После сбора — повторная валидация на всех задачах пула (`run_id gold_post`) и таблица расхождений gold_pre /
  gold_post. Что делать с задачами, где эталон перестал проходить, решает автор.

### 11.8. Порядок основного сбора

- Имя прогона: `own-v1.2_mini-v1.17.1_glm-4.6_main_r<k>_<задача>`, `protocol_version = 1.2`, конфиг
  `config/glm-4.6_v1.1.yaml` без изменений. У 4 задач пилота повторы 0–2 — прогоны пилота `..._pilot_r<k>_<задача>`
  (протокол 1.1, 11.4).
- **По кругам:** сначала повтор 0 всех задач (порядок `tasks_main.json`), затем повтор 1, затем повтор 2 — при
  остановке по бюджету покрытие равномерное. Строго по одному прогону.
- После трёх повторов всех задач: задачи со смешанным исходом (среди повторов 0–2 есть и 0, и 1) — первые 30 по
  порядку `tasks_main.json` — получают повторы 3 и 4, тоже по кругам.
- После каждого прогона: оценка, разбор адаптером, проверка на ключ, строка в `LOG.md`, проверка расхода. Коммит и
  push каждые 10 прогонов.
- Продолжение с места остановки: прогон с готовой меткой пропускается. Незавершённый прогон (остатки в WSL, нет
  вывода) и технический сбой переносятся в `raw_failed/<run_id>-attempt<N>/` и повторяются под тем же `run_id`.
  Технический сбой — любой статус выхода, кроме исходов агента `Submitted` и `LimitsExceeded`: ошибки API
  (`infra_exit_statuses` из `config/datasets.yaml`, `RetryError` после исчерпания повторов), ошибки Docker и среды.
  В этих случаях mini-swe-agent пишет в патч текст исключения.
- Метка прогона с пустым патчем (агент ничего не изменил или вышел по лимиту: при `LimitsExceeded` патч пуст) — 0 «не
  решено»: harness такие патчи не оценивает и `report.json` не пишет (как в 11.1). Если оценка дважды не дала
  `report.json` при непустом патче, прогон остаётся без метки (`eval/<run_id>/EVAL_FAILED.json`) и отмечается в
  `LOG.md`.
- Остановка: расход ≥ $35; ключ API в файлах; рассуждения в тексте или отличие конфига; 3 технических сбоя подряд.
- После сбора — `STAGE4_REPORT.md`: число прогонов, расход, время, распределение исходов по задачам, задачи со
  смешанным исходом и пары внутри задачи, результат gold_post. Анализ (AUROC, McNemar) — отдельный этап.
