# Задача для Claude Code: тест E6 — доработка модели и внешняя валидация

## Контекст

Тема утверждена: «Разработка модели оценки достоверности утверждений LLM-агентов о выполнении
задачи на основе структуры траектории выполнения».

Текущее состояние (не переделывать, использовать как базу):
- `M_struct+len` — AUROC 0.684 [0.659; 0.709], внутри задач 0.646;
- перенос между семействами моделей — медианное падение 0.011;
- сильнейший признак — энтропия биграмм фаз (|SHAP| 0.315);
- калибровка: Бриер 0.203 против 0.227 у константы.

E6 решает четыре задачи: починить сломанные признаки, устранить коллинеарность, добавить метрику
практической полезности, проверить модель на другом домене.

Модуль `src/e6_refine.py`, команда `python -m src.cli e6`. Существующие скрипты не менять.
Все правила протокола прежние: `GroupKFold` по `task_id`, кластерный бутстрэп по задачам
(1000 итераций), seed 42, логистическая регрессия с L2 без подбора гиперпараметров.

## Блок 1. Починка признаков

### 1.1. Детектор зацикливания

Сейчас `repeat_ratio` равен 0.003–0.004, то есть не срабатывает: правило «подряд идущие
идентичные команды» слишком строгое.

Переписать:
- **нормализация команды** перед сравнением: убрать пути к временным файлам, номера строк,
  хеши, лишние пробелы; оставить имя команды и ключевые аргументы;
- `repeat_ratio_norm` — доля подряд идущих нормализованно одинаковых команд;
- `repeat_in_window_k` — доля шагов, чья нормализованная команда уже встречалась в предыдущих
  k шагах, для k = 3, 5, 10;
- `max_run_length` — длина максимальной серии одинаковых нормализованных команд;
- `distinct_ratio` — отношение числа уникальных нормализованных команд к числу шагов;
- `revisit_ratio` — доля шагов, возвращающихся к уже открытому ранее файлу.

Для каждого нового признака вывести AUROC в одиночку и долю ненулевых значений. Признак
с долей ненулевых ниже 5% считать неработающим и исключить, отметив это в отчёте.

### 1.2. Доля неуспешных команд

`nonzero_rc_share` даёт коэффициент ровно 0 — коды возврата, видимо, не извлекаются.

Разобраться: проверить, присутствуют ли коды возврата в сыром логе. Если отсутствуют — заменить
текстовым прокси:
- доля шагов, в выводе инструмента которых есть признаки ошибки: `Traceback`, `Error`,
  `No such file`, `command not found`, `SyntaxError`, `FAILED`, ненулевой `exit status`;
- отдельно — доля шагов с ошибкой **среди шагов верификации**.

В отчёте указать, какой вариант использован и почему.

### 1.3. Признаки последовательности длиннее биграмм

- энтропия Шеннона по распределению **триграмм** фаз;
- частоты десяти самых распространённых биграмм и триграмм как отдельные признаки;
- длина самой длинной серии одной фазы подряд;
- индикатор «после последней правки была хотя бы одна верификация, и она была не первой»
  (повторная проверка).

## Блок 2. Устранение коллинеарности

1. Удалить дубль: `seg_len_steps` и `n_steps_after_last_edit` — одна и та же величина.
2. Построить матрицу корреляций всех признаков и фактор инфляции дисперсии (VIF).
3. Для каждой группы признаков с попарной корреляцией |r| > 0.8 оставить **один** —
   тот, что выше по одиночному AUROC. Решение и причину зафиксировать в отчёте.
4. Пересчитать модель на очищенном наборе. Сравнить с текущей: если AUROC не упал более чем
   на 0.01, использовать очищенный набор как основной — интерпретируемость важнее.
5. Таблицу коэффициентов публиковать только для очищенного набора; для полного — только SHAP.

## Блок 3. Метрика практической полезности

AUROC не говорит, что модель даёт на практике. Добавить:

- **precision@k** при бюджете проверок k = 5%, 10%, 20% самых подозрительных прогонов;
- **lift@k** — во сколько раз доля недостоверных в отобранной выборке выше базовой (0.348);
- **recall@k** — какую долю всех недостоверных утверждений ловим при таком бюджете;
- таблица «бюджет проверок → сколько недостоверных найдено → сколько проверок потрачено впустую».

Это основная таблица для раздела о практической значимости.

Дополнительно: изотоническая калибровка на обучающих фолдах, пересчёт меры Бриера и кривой
надёжности. Сейчас на верхнем бине модель переоценивает риск (предсказано 0.735,
наблюдается 0.684).

## Блок 4. Внешняя валидация

Проверить, переносится ли модель на другой домен.

**Источник:** набор траекторий агентов из другого бенчмарка с метками успеха — AppWorld,
τ²-bench или аналогичный мультидоменный корпус. Требования к источнику те же: бинарная метка
из среды (не от LLM-судьи), идентификатор задачи, текст шагов, известная модель.

**Что сделать:**
1. Адаптер в `src/adapters/`, приводящий к той же схеме.
2. Разметка утверждений теми же правилами — **сначала проверить применимость**: доля
   утверждений среди провальных в новом домене, сравнить с 36.9%. Если правила не переносятся
   (доля близка к нулю), адаптировать паттерны и зафиксировать это отдельно.
3. Фазовая разметка: команды в другом домене другие, правила придётся расширить. Сохранить
   отображение в те же четыре фазы.
4. Два режима:
   - **перенос без дообучения** — модель, обученная на SWE-bench, применяется к новому домену;
   - **обучение на новом домене** — модель обучается с нуля, сравнение качества.
5. Сравнить важность признаков между доменами: сохраняется ли энтропия биграмм фаз
   в числе ведущих.

**Если подходящего источника не найдено** — зафиксировать это в отчёте с перечнем проверенных
вариантов и причин отказа. Не подменять внешнюю валидацию разбиением того же корпуса.
