# Спецификация работы: раннее прогнозирование провала LLM-агентов по хаотичности семантических траекторий

Документ для Claude Code. Это техническое задание на разведочное исследование, а не на продукт.
Цель работы — получить **честный ответ «да/нет»** на вопрос, несут ли динамические характеристики
семантической траектории агента информацию о будущем провале задачи сверх тривиальных признаков.

Отрицательный результат — допустимый и ожидаемый исход. Задача пайплайна — не «показать, что метод
работает», а измерить, работает ли он. Любая подгонка под положительный результат обесценивает работу.

---

## 0. Контекст

Магистерская диссертация, AITU, программа Applied AI.
Тема: «Разработка модели раннего прогнозирования неуспешного выполнения задач LLM-агентами
на основе оценки хаотичности семантических траекторий».

Идея: трасса агента (рассуждения + вызовы инструментов) после эмбеддинга каждого фрагмента
образует траекторию в семантическом пространстве. Гипотеза: траектории, ведущие к провалу задачи,
отличаются по динамическим характеристикам (перестановочная энтропия, статистическая сложность)
от траекторий, ведущих к успеху, и это различие видно уже на префиксе траектории.

## 1. Уже установленные факты — принимать как ограничения, не переоткрывать

Проведена симуляция оценщика перестановочной энтропии (`ordpy`, 400 повторов на ячейку).
Результаты фиксируют дизайн:

**1.1. Смещение оценки зависит от длины ряда.** Для белого шума, где нормированная энтропия
обязана быть 1.0:

| n точек | d=3 | d=4 | d=5 |
|---|---|---|---|
| 20 | 0.943 | 0.780 | 0.565 |
| 50 | 0.979 | 0.919 | 0.752 |
| 100 | 0.990 | 0.964 | 0.858 |
| 500 | 0.998 | 0.993 | 0.974 |

**1.2. Разделимость реалистичного по размеру эффекта (AUROC, d=4):**
n=20 → 0.54; n=50 → 0.59; n=100 → 0.64; n=200 → 0.69; n=500 → 0.87.

**Следствия, обязательные к исполнению:**

- **Шаговое разрешение запрещено как основное.** Траектории агентов содержат десятки шагов;
  при такой длине метод неразличим от шума. Базовая единица траектории — **предложение/фрагмент**,
  а не шаг агента.
- **Длина окна фиксируется жёстко.** Сравнивать признаки рядов разной длины нельзя: смещение
  оценки само по себе создаст «сигнал», коррелирующий с длиной траектории, а длина коррелирует
  с провалом. Из каждой траектории берутся **ровно первые N фрагментов**; траектории короче N
  исключаются и этот факт логируется.
- **Основной порядок паттернов d=4.** d=3 — для контроля на коротких окнах, d=5 — только при N≥500.

## 2. Данные

### 2.1. Требования к источнику

Набор траекторий пригоден, только если выполнены все условия:

1. есть **бинарная метка исхода** (задача решена / не решена), полученная средой или тестами,
   а не LLM-судьёй;
2. есть **идентификатор задачи** (`task_id`), и по одной и той же задаче присутствуют прогоны
   обоих классов — это необходимо для сравнения внутри задачи;
3. доступен **текст** шагов (рассуждения агента), а не только агрегаты;
4. известен **агент/модель**, породившая трассу (для контроля переноса).

### 2.2. Кандидаты, в порядке приоритета

1. **Траектории с лидерборда SWE-bench Verified** — полная матрица «агент × задача»
   (около 19 агентов × 500 задач), метка из прогона тестов. Идеально по пункту 2.
2. **Exgentic/agent-llm-traces-v2** (Hugging Face) — ~10 тыс. прогонов на шести бенчмарках
   (AppWorld, SWE-bench, BrowseCompPlus, τ²-bench ×3). Нужен для проверки переноса между доменами.
3. **nvidia/Open-SWE-Traces** — 200k+ траекторий SWE-agent/OpenHands, CC BY 4.0. Резерв на случай
   нехватки объёма.
4. **Mahmoud-queens/swe-agent-subset-selection-vectors** — уже посчитанные эмбеддинги **по шагам**
   с метками SUCCESS/FAIL. Использовать **только** для быстрой проверки пайплайна тестов
   (этап E4) и как явно помеченный «шаговый» контрольный вариант. Основные выводы на нём строить
   нельзя — см. п. 1.

### E1. Сегментация и эмбеддинг

**Что сделать**

Построить три варианта сегментации, они сравниваются на E4:

- `seg=reason_sent` — **основной**: берутся только сообщения `role=assistant`, текст режется
  на предложения (`blingfire` или `nltk.punkt`; для кода — по строкам, но блоки кода длиннее
  10 строк усекаются до первых 10);
- `seg=all_sent` — то же, но включая тексты `role=tool` (проверка влияния логов и выводов инструментов);
- `seg=step` — по шагам агента, **только как контроль**, чтобы эмпирически подтвердить п. 1.

Правила очистки (применяются до эмбеддинга):
- убрать ANSI-escape, трейсбеки длиннее 20 строк усечь до первых 5;
- фрагменты короче 15 символов отбрасываются;
- маркеры из `leak_markers.txt` заменяются на `[MASKED]`;
- нормализация пробелов, без lowercase (эмбеддер сам справится).

Эмбеддинг:
- основной энкодер `sentence-transformers/all-MiniLM-L6-v2` (384d, быстрый на CPU);
- контрольный энкодер `nomic-ai/nomic-embed-text-v1.5` (768d) — прогоняется на подвыборке
  в 300 траекторий для проверки, что выводы не зависят от энкодера;
- батчами, с кэшем на диск (`data/emb/{seg}/{run_id}.npy`, float32), чтобы повторные прогоны
  не пересчитывали.

**Критерий приёмки:** при `seg=reason_sent` медиана длины траектории в фрагментах ≥ 200.
Если медиана < 200 — сегментация дробится мельче (клаузы вместо предложений) и E1 повторяется.
Если и это не даёт 200 — зафиксировать в отчёте и перейти к E2 с N=100, пометив ограничение.

### E2. Проекция в одномерный ряд

Из траектории `(T, D)` получить ряд `(T,)`. Реализовать все четыре, ни одну не выбирать заранее:

- `proj=cos_step` — косинусное расстояние между соседними фрагментами (скорость движения по смыслу);
- `proj=cos_task` — косинусное расстояние фрагмента до эмбеддинга постановки задачи
  (удаление от цели);
- `proj=pca1` — проекция на первую главную компоненту, PCA обучается **на обучающей части и только
  на ней**, иначе утечка;
- `proj=norm` — норма разности соседних эмбеддингов (контрольная, самая грубая).

**Критерий приёмки:** для каждой проекции посчитать долю рядов, статистически неотличимых
от белого шума (тест на автокорреляцию первого порядка, Ljung–Box). Если для всех проекций
эта доля > 90% — сигнала в динамике нет в принципе; зафиксировать и остановиться.

### E3. Признаки

Для каждой комбинации `(seg, proj, N ∈ {100, 200, 400}, d ∈ {3, 4})` посчитать:

**Признаки хаотичности** (`ordpy`, на первых N точках ряда):
- `H` — нормированная перестановочная энтропия;
- `C` — статистическая сложность Хименеса–Крепса–Ларрондо;
- `fisher` — информация Фишера–Шеннона (опционально).

**Базовые (тривиальные) признаки** — обязательны, это конкурент, которого надо обойти:
- `n_steps` — число шагов агента;
- `n_frag` — число фрагментов;
- `total_chars` — суммарная длина текста;
- `mean_frag_len` — средняя длина фрагмента;
- `n_tool_calls` — число вызовов инструментов;
- `repeat_ratio` — доля повторяющихся вызовов инструментов подряд (простой детектор зацикливания).

**Важно:** все признаки считаются **только по первым N фрагментам**, никогда по всей траектории.
Траектории с числом фрагментов < N исключаются, число исключённых логируется отдельно по классам
(если исключение асимметрично по классам — это смещение выборки, его надо зафиксировать в отчёте).

**Выходной артефакт — `outputs/features.csv`, схема фиксирована:**

```
run_id, task_id, agent_id, model_id, label,
seg, proj, N, d,
H, C, fisher,
n_steps, n_frag, total_chars, mean_frag_len, n_tool_calls, repeat_ratio
```

Одна строка = одна комбинация (траектория × seg × proj × N × d).

### E4. Статистические тесты

Все тесты — в `reports/E4_results.md` плюс машиночитаемый `outputs/summary.csv`.

#### Тест 3 — различение внутри задачи

Для каждой задачи с парами обоих классов: сравнить распределения `H` и `C` между классами
(Манна–Уитни), посчитать размер эффекта (ранг-бисериальная корреляция).
Свести: доля задач со значимым различием (с поправкой Бенджамини–Хохберга), медианный размер
эффекта, **доля задач, где эффект направлен в одну и ту же сторону**.

Разнонаправленный эффект — тревожный признак, о нём надо написать явно.

#### Тест 4 — инкрементальность над тривиальными признаками (критический)

Три логистические регрессии на одних данных:

1. `M_base` — только базовые признаки;
2. `M_chaos` — только `H`, `C`;
3. `M_full` — все.

Правила:
- кросс-валидация **GroupKFold по `task_id`**, 5 фолдов. Одна и та же задача никогда не попадает
  одновременно в train и test;
- метрики: AUROC, PR-AUC, precision при фиксированной доле алертов 10%;
- разница AUROC между `M_full` и `M_base` — с доверительным интервалом (бутстрэп по задачам,
  1000 итераций);
- отдельно посчитать корреляцию Спирмена между `H` и `n_frag`, `H` и `n_steps`. Высокая корреляция
  означает, что признак вторичен по отношению к длине.

**Критерий успеха темы:** нижняя граница 95% ДИ прироста AUROC (`M_full` − `M_base`) > 0.

#### Тест 5 — ранний прогноз

Повторить тест 4 для N ∈ {50, 100, 200, 400} и построить кривую «объём увиденного префикса →
AUROC». Отдельно: доля траектории в процентах, при которой AUROC впервые превышает 0.65.

#### Тест 6 — перенос

Обучить на траекториях одного семейства агентов/моделей, протестировать на другом.
Аналогично — обучить на одном бенчмарке, проверить на другом (если используется источник №2).
Сообщить падение AUROC.

## 4. Жёсткие правила корректности

Нарушение любого из них делает результат недействительным.

1. **Никакой настройки на тестовой части.** Выбор `seg`, `proj`, `N`, `d` производится
   по кросс-валидации на обучающих фолдах; финальный прогон — один раз.
2. **Группировка по задаче во всех разбиениях.** Всегда `GroupKFold(task_id)`.
3. **Фиксированная длина окна** при любом сравнении признаков (п. 1.2).
4. **Префикс не содержит будущего.** Никаких признаков, вычисленных по последним шагам,
   никакого финального ответа, никаких меток из метаданных трассы.
5. **Все случайные операции с фиксированным seed = 42**, версии библиотек закреплены в `requirements.txt`.
6. **Множественные сравнения корректируются** (Бенджамини–Хохберг) — комбинаций (seg × proj × N × d)
   много, и часть «находок» будет случайной.
7. **Логировать отброшенное**: сколько траекторий исключено и по какой причине, в разрезе классов.

## 5. Чего делать НЕ надо

- Не обучать нейросети, не файнтюнить LLM, не использовать LLM-судей. Метод должен остаться
  дешёвым, интерпретируемым и не требующим обучения — в этом его позиционирование против
  существующих работ.
- Не строить веб-интерфейсы, дашборды, API. Результат работы — таблицы и графики.
- Не оптимизировать гиперпараметры классификатора. Логистическая регрессия с L2 и стандартным
  масштабированием, без подбора. Сравниваются признаки, а не модели.
- Не добавлять признаки «на всякий случай». Каждый новый признак расширяет пространство
  множественных сравнений.
- Не переходить к следующему этапу, если критерий приёмки предыдущего не выполнен.
