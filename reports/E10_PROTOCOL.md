## 1. Идея и вопрос

Модель `S` знает, что агент запускал проверки, но не знает, чем они кончились. Блок O извлекает исход собственных
проверок агента из ответов среды. Это информация, доступная агенту во время работы. Скрытые тесты SWE-bench и эталонный
патч не используются.

**Вопрос:** добавляет ли блок O сигнал сверх `S` в трёх местах:
- внутри попыток одной модели (повторы KTH);
- на лидерборде;
- при выборе лучшей попытки (код E9).

## 3. Проверки

**Проверка** — исполненная команда (вызов инструмента), для которой выполнено хотя бы одно:
- `demo_lib` классифицирует один из её сегментов как «проверку» (фаза verify);
- в ней есть запуск тестов. Регулярное выражение:
  - `pytest`, `py.test`;
  - `python -m (pytest|unittest|nose)`;
  - `runtests(.py)`, `bin/test`, `tox`, `nosetests`;
  - `make test`;
  - `(django-admin|manage.py|python -m django) test`.

Вывод команды — вывод инструмента того же шага. Если в шаге несколько вызовов и столько же выводов, они сопоставляются
по порядку. Если число выводов не совпадает с числом вызовов, проверка получает `unknown` (причина
`unpaired_output`).

**Запускались тесты проекта или самодельный скрипт агента.**
- **Тесты проекта** — проверка запускает тестовую программу (регулярное выражение выше), и выполнено хотя бы одно:
  - программа — собственная программа проекта: `runtests.py`, `bin/test`, `tox`, `make test`, тесты django;
  - среди аргументов есть путь с каталогом `tests/` или `testing/`, или метка вида `tests.…`;
  - путей и меток нет вовсе: pytest собирает тесты проекта.
- **Самодельный скрипт** — все остальные проверки. Например, `python reproduce.py` с `assert`, `python -c` с
  `assert`, pytest по файлу вне `tests/` и `testing/`.
- **Ограничение.** Файл, который агент сам создал внутри `tests/`, считается тестом проекта.

## 4. Разбор исхода проверки

Категории: `pass`, `fail`, `error`, `unknown`. Правила применяются по порядку, первое сработавшее решает.

1. **Итоговая строка тестовой программы.** Если таких строк несколько, берётся последняя.
   - **pytest:** строка вида `[=…] N failed, M passed, K error(s) … in X s [=…]` или `no tests ran in X s`.
     - failed > 0 → `fail`;
     - иначе error(s) > 0 → `error`;
     - иначе passed > 0 → `pass`;
     - `no tests ran` → `error`.
   - **unittest и django runtests:** `Ran N tests in …`, затем `OK` или `FAILED (failures=a, errors=b)`.
     - `OK` при N > 0 → `pass`;
     - `Ran 0 tests` → `error`;
     - `FAILED` при a = 0, b > 0 и наличии в выводе `ImportError`, `ModuleNotFoundError`, `SyntaxError` или
       `Failed to import test module` → `error`;
     - любой другой `FAILED` → `fail`.
   - **sympy `bin/test`:** `tests finished: N passed, M failed, … K exceptions …`.
     - M > 0 или K > 0 → `fail`;
     - иначе N > 0 → `pass`.
2. **Ошибка сбора или импорта** (итоговой строки нет): в выводе есть `ImportError`, `ModuleNotFoundError`,
   `SyntaxError`, `No module named`, `errors? during collection`, `collected 0 items`, `ERROR: file or directory not
   found`, `ERROR: not found`, `can't open file` или `command not found` → `error`.
3. **Падение самодельного скрипта**: `Traceback (most recent call last)` или `AssertionError` → `fail`.
4. **Итог недоступен** → `unknown`, если выполнено хотя бы одно:
   - вывод обрезан самим агентом: вывод команды направлен в `head`, `tail` или `grep`;
   - mini-SWE-agent пометил вывод как слишком длинный («output … too long», «characters elided»);
   - nano-agent обрезал вывод («output truncated»);
   - сработал тайм-аут (`timed out`, `TimeoutExpired`).
5. **Самодельный скрипт без признаков выше и с кодом возврата 0** → `pass`.
6. **Всё остальное** → `unknown`. Например, тестовая программа без итоговой строки или ненулевой код возврата без
   traceback.

Для каждой проверки записываются категория, правило, сработавшая строка и число упавших тестов:
- pytest: failed + errors;
- unittest: failures + errors;
- sympy: failed + exceptions;
- `fail` самодельного скрипта — 1;
- иначе 0.

## 6. Признаки блока O (на прогон)

Проверки упорядочены по шагам, внутри шага — по порядку вызовов. «Перед отправкой» означает вся траектория: патч и
финальное сообщение отправки в ней не содержатся.

| признак | определение |
|---|---|
| `o_ran_project_tests` | 1, если была хотя бы одна проверка тестами проекта |
| `o_last_status_{pass,fail,error,unknown}` | one-hot исхода последней проверки; без проверок — все 0 |
| `o_last_project_status_{pass,fail,error,unknown}` | то же для последней проверки тестами проекта |
| `o_n_fail` | число проверок с исходом `fail` или `error` |
| `o_share_fail` | `o_n_fail` / число проверок (0 без проверок) |
| `o_unresolved_fail` | 1, если была проверка `fail` или `error`, после которой до конца траектории нет проверки `pass` |
| `o_edit_after_last_pass` | 1, если после последней проверки `pass` была правка (событие `edit` `demo_lib` в более поздней команде); без `pass` — 0 |
| `o_last_fail_count` | число упавших тестов последней проверки; 0, если её исход `pass`, `unknown` или `error`, или проверок не было |
| `o_contradiction` | 1, если финальное сообщение содержит заявление об успехе по детектору G0, а последняя проверка — `fail` или `error` |

Детектор G0 — `config/claim_patterns.txt` через `g0.match_any`. Его шаблоны уже включают «tests pass» и «all tests
passed». На лидерборде результат сверяется с `outputs/g0_final_messages.csv` (`has_claim`).

**Блок O — 15 признаков:** 1 + 4 + 4 + 1 + 1 + 1 + 1 + 1 + 1.

Для `o_last_fail_count` при исходе `error` берётся 0. Задание это не оговаривает: при ошибке сбора тесты не
запускались, поэтому упавших тестов нет.

**Доля `unknown`.** Для лидерборда — по связкам (модель × версия агента), для KTH — по настройкам. Считаются две
доли:
- среди всех проверок;
- среди последних проверок прогонов.

Где доля выше 50%, это записывается как ограничение.

## 7. Лидерборд — протокол E7

- Популяция — `submitted == 1`, 7864 прогона, по `run_id`.
- Фолды E7: `GroupKFold(5, shuffle=True, random_state=42)` по `task_id`.
- Модель — `StandardScaler` + `LogisticRegression(C=1, max_iter=5000)`, без подбора.
- `M` — one-hot связки, кодировщик обучен на обучающем фолде.

**Модели:** `O`, `S`, `S+O`, `M+S`, `M+S+O`.

**Метрики:**
- общий AUROC;
- AUROC внутри задачи;
- precision@10%;
- Brier;
- AUROC в парах моделей почти равной силы, как в дополнении E7. Сила связки — доля решённых ею по популяции, пары
  внутри задачи с |разницей силы| < 0.03.

**Интервалы.** 95% ДИ — кластерный бутстрэп по задачам: 1000 общих выборок, `default_rng(42)`, те же выборки, что
в E7. Разности считаются на тех же выборках:
- `S+O` − `S`;
- `M+S+O` − `M+S`.

**Проверка воспроизведения:** `S` даёт 0.662 и 0.640, `M+S` — 0.685, как в E7.

## 8. Повторы KTH — протокол E8 и код E9

- Популяция — E8: 13 778 прогонов с меткой.
- Модели `S`, `O`, `S+O` обучаются **внутри своей настройки**. `GroupKFold(5, shuffle=True, random_state=42)` по
  задаче на популяции настройки, по `run_id` — это фолды E9.
- **AUROC внутри единицы** (настройка × задача):
  - 95% ДИ — бутстрэп по единицам, 1000, `default_rng(42)`;

  - поправка Холма по трём настройкам для каждой модели;
  - разность `S+O` − `S` — на тех же выборках;
  - по каждой настройке и для трёх вместе.
- **Выбор лучшей попытки** — код E9 (`src/e9_best_of_k.py`):
  - подвыборки и бутстрэп по задачам те же, что в E9;
  - Δ доли решённых к submitted-random при k = 5 для `S` и `S+O`, по настройкам и для трёх вместе;
  - разность Δ(`S+O`) − Δ(`S`) с 95% ДИ.
  - Признаки `S` и `O` для 34 попыток с ошибкой оценки считаются тем же кодом из траекторий, риск — как в E9.
  - **Проверка:** `S` здесь совпадает с P2 из E9, Δ при k = 5 — +0.77 / −0.61 / −1.25 п.п.

## 9. Критерии

Записаны до расчётов.

- **К1. O добавляет сигнал уровня попытки.** На KTH, три настройки вместе, нижняя граница 95% ДИ разности `S+O` −
  `S` по AUROC внутри единиц > 0.
- **К2. Практически значимо.** AUROC внутри единиц у `S+O` ≥ 0.60 (точечная оценка) хотя бы в одной настройке.
- **К3. Лидерборд.** Нужны оба условия:
  - нижняя граница 95% ДИ разности `S+O` − `S` по общему AUROC > 0;
  - разность `S+O` − `S` в парах равной силы > 0. По формулировке задания это точечная оценка, её 95% ДИ
    сообщается.
- **К4. Отбор становится лучше.** Нижняя граница 95% ДИ разности Δ(`S+O`) − Δ(`S`) при k = 5 > 0 хотя бы в одной
  настройке. Поправка не применяется: формулировка «хотя бы в одной» без поправки.

**Описательно, без критерия**, по корпусам и настройкам:
- доля прогонов с `o_contradiction` = 1 и доля решённых среди них;
- доля решённых при `o_last_status` = `pass` и при `fail`.

## 11. Изменения после проверки разбора (2026-11-05, до основных расчётов)

Записаны после четырёх раундов проверки разбора автором (`reports/E10_parser_check.md`). Признаки, модели и метрики
до этого не считались.

### 11.1. Источник лидерборда (к разделу 2)

- В разделе 2 сказано, что исходных `.traj.json` на диске нет. Это неверно: локально лежат 355 файлов (16 связок).
- Сверка на 5 прогонах популяции: 204 из 204 выводов команд совпадают байт в байт с `trajectories.jsonl.gz` после
  снятия обёртки mini-SWE-agent. Разбор остаётся на `trajectories.jsonl.gz`, скачивание не нужно.

### 11.2. Проверки (к разделу 3)

- Самодельный скрипт, который пишет в файлы репозитория, — не проверка. Скрипт, который команда создаёт и тут же
  запускает, — проверка.
- Путь в аргументах тестовой программы разрешается от текущего каталога с учётом `cd` в той же команде. Файл вне
  `/testbed` — не тест проекта.
- Файл, который агент создал раньше в том же прогоне (`cat >`, `echo >`, `tee`, `open(…, 'w')` без чтения этого
  файла тем же кодом), — скрипт агента, а не тест проекта, в том числе внутри `tests/`. «Ограничение» раздела 3 снято.

### 11.3. Категории исхода (к разделу 4)

Семь категорий вместо четырёх:
- тесты проекта: `pass`, `fail`, `error_env`, `error_code`, `unknown`;
- самодельные скрипты: `script_ok`, `script_fail` вместо `pass` / `fail`; `error_env`, `error_code`, `unknown` — как у
  тестов проекта.

`error_env` — агент не смог запустить проверку: нет программы, неверный путь или метка, не настроено окружение,
сломан сам скрипт. `error_code` — сломан код проекта: SyntaxError, ImportError или traceback при загрузке модуля из
файлов репозитория. Правила разбора — `reports/E10_parser_check.md`, раунды 1–4.

### 11.4. Признаки (к разделу 6)

Два набора признаков (решение автора по раунду 3, п. 5).

**Основной набор — по отдельным категориям, 19 признаков.** На нём проверяются критерии К1–К4.

| признак | определение |
|---|---|
| `o_ran_project_tests` | как в разделе 6 |
| `o_last_status_{pass, fail, error_env, error_code, script_ok, script_fail, unknown}` | one-hot исхода последней проверки, 7 значений; без проверок — все 0 |
| `o_last_project_status_{pass, fail, error_env, error_code, unknown}` | то же для последней проверки тестами проекта, 5 значений |
| `o_n_fail` | число проверок тестами проекта **после первой правки кода проекта** (11.5) с исходом `fail`, `error_env` или `error_code` |
| `o_share_fail` | `o_n_fail` / число проверок тестами проекта после первой правки кода проекта; 0, если их нет |
| `o_unresolved_fail` | 1, если после первой правки кода проекта была проверка тестами проекта с исходом `fail` или `error_*`, после которой до конца траектории нет проверки тестами проекта с исходом `pass` |
| `o_edit_after_last_pass` | 1, если после последней проверки тестами проекта с исходом `pass` была правка (как в разделе 6); без такой проверки — 0 |
| `o_last_fail_count` | число упавших тестов последней проверки тестами проекта, если её исход `fail`; иначе 0 |
| `o_contradiction` | 1, если финальное сообщение заявляет успех (G0), а последняя проверка тестами проекта — `fail` или `error_*` |

В шести последних признаках «pass / fail / error» раздела 6 — это категории тестов проекта. Исход самодельных
скриптов в них не входит: автор требовал не смешивать его с исходом тестов проекта (замечания к раунду 2, п. 4).
Скрипты входят в основной набор через `o_last_status_script_ok` / `_script_fail`, а также через `error_*` и `unknown`
последней проверки. Буквальное прочтение — `pass`, `fail`, `error_*` по всем проверкам — смешало бы скрипты
частично: падение скрипта на печати символа (`error_env`) считалось бы провалом, а `script_fail` — нет.

**Дополнительный набор — по объединённым категориям, 15 признаков.** Это признаки раздела 6 в точности как записаны,
по всем проверкам, с категориями:
- pass = `pass` ∪ `script_ok`;
- fail = `fail` ∪ `script_fail`;
- error = `error_env` ∪ `error_code`.

`o_last_project_status` здесь — четыре значения (pass, fail, error, unknown) для тестов проекта. Изменение 11.5
действует и в этом наборе. Модели с дополнительным набором — проверка устойчивости: они сообщаются рядом с основными,
критерии К1–К4 по ним не проверяются.

### 11.5. Проверки до первой правки кода проекта (к разделу 6)

- `o_n_fail`, `o_share_fail` и `o_unresolved_fail` считаются только по проверкам после первой правки кода проекта, в
  обоих наборах.
- **Причина** (замечание автора F к раунду 3). Ранние проверки — воспроизведение ошибки до исправления, их провал
  ожидаем (в выборке seed 45 — №81, 83, 84, 86). Без этого изменения признаки провала смешивают воспроизведение ошибки
  с неудачей исправления.
- **Правка кода проекта** — сегмент команды, который пишет файл исходников репозитория (каталоги исходников —
  `reports/E10_parser_check.md`, раунд 3, п. 3), и это не файл тестов:
  - в пути нет каталога `tests/`, `test/`, `testing/`;
  - имя файла не `test_*`, `*_test.py`, `*_tests.py`, `conftest.py`.
- Запись — `>`, `>>`, `tee`, `sed -i`, `perl -i`, запись из python (`open(…, 'w'|'a')`, `.write_text`), правка
  `apply_patch` в KTH. Запись из python считается и при запуске скрипта, записанного раньше в прогоне
  (`cat > /tmp/patch.py`, затем `python /tmp/patch.py`). `git apply` и `patch` тоже считаются правкой кода: файл по
  команде неизвестен. Путь разрешается от текущего каталога.
- Проверка в той же команде, что и первая правка, идёт «после», если её последний сегмент стоит после сегмента правки.
- Если правка кода проекта не найдена, эти три признака равны 0. Доля таких прогонов сообщается.
- `o_last_status_*`, `o_last_project_status_*`, `o_edit_after_last_pass`, `o_last_fail_count`, `o_contradiction` —
  по всем проверкам, как раньше.
