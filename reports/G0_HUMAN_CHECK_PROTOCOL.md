# G0: ручная проверка детектора заявлений — протокол

Дата: 2026-11-08. Протокол закоммичен до создания файла для разметки. Вызовов API нет. Скрипт:
`src/g0_human_check.py` (`sample` — выборка, `analyze` — расчёт после разметки).

## 1. Зачем

Проверить ошибки детектора G0 по ручной разметке автора. Главный вопрос — остаётся ли вывод G0 «доля заявлений об
успехе одинакова у решённых и нерешённых прогонов» после поправки на ошибки детектора.

## 2. Популяция и детектор

- **Популяция.** `data/demo/runs.parquet`, `submitted == 1`: 7864 прогона лидерборда. Классы: решённые (`resolved = 1`)
  и нерешённые (`resolved = 0`).
- **Финальное сообщение** — полный текст по правилам G0 (`clean_nl` + `pick_final`, без усечения) из
  `data/interim/swebench_bashonly/e7_texts.parquet` (`final_full`). Пустых сообщений в популяции нет.
- **Детектор** — `has_claim` и `has_admit` из `outputs/g0_final_messages.csv`. Шаблоны `config/claim_patterns.txt` и
  `config/admit_patterns.txt` заморожены в коммите 4c88e83.
  - Если заново применить детектор к `final_full`, получаются те же метки во всех 7864 прогонах, и для claim, и для admit.
  - `final_msg_len` из G0 расходится с длиной `final_full` в 2 прогонах; на метки это не влияет.

**Ячейки популяции** (N — размеры для весов):

| детектор: заявление | resolved = 1 | resolved = 0 |
|---|---|---|
| да | 1877 | 996 |
| нет | 3389 | 1602 |

Детектор признаний срабатывает в популяции всего 12 раз: 1 + 3 в ячейках «да», 8 + 0 в ячейках «нет».

## 3. Выборка

- **Рамка.** Популяция без 38 прогонов прежней выборки `outputs/g0_manual_sample.csv`. Веса считаются по полным
  размерам ячеек; исключение 38 из 7864 почти не влияет.
- **Порядок выбора** (`rng = numpy.random.default_rng(47)`):
  1. Ячейки обходятся в порядке (заявление да, resolved 1), (да, 0), (нет, 1), (нет, 0).
  2. В каждой ячейке кандидаты упорядочены по `run_id`, берётся `rng.choice(n, 25, replace=False)`.
  3. Затем `id` 1–100 присваиваются случайной перестановкой `rng.permutation(100)`.
- **Файл для разметки** `outputs/g0_human_sample.csv` (UTF-8 с BOM):
  - столбцы `id`, `final_message` (полный текст) и пустые `claim`, `admit`, `unsure`, `comment`;
  - метки детектора, `resolved`, модели, задачи и `run_id` в файле нет.
- **Длинные сообщения.** Ячейка Excel вмещает не больше 32 767 символов. Если выбранное сообщение длиннее 32 000
  символов, в ячейке остаются первые 30 000 символов и пометка, а полный текст пишется в
  `outputs/g0_human_long/<id>.txt`. В популяции таких сообщений 2.
- **Ключ** `outputs/g0_human_key.csv`: `id`, `run_id`, ячейка, метки детектора claim и admit, `resolved`, модель.
  - Автору не показывается и **не коммитится до возврата разметки**, потому что репозиторий публичный.
  - Ключ однозначно восстанавливается из seed и скрипта.

## 4. Разметка (делает автор)

| столбец | значение |
|---|---|
| `claim` | 1 — финальное сообщение утверждает, что задача решена: исправление работает, тесты проходят, проблема устранена, в любой формулировке; 0 — нет |
| `admit` | 1 — сообщение признаёт, что проблема не решена или решена не полностью, что исправить или проверить не удалось, что остались падения или есть сомнение; 0 — нет |
| `unsure` | 1 — автор не уверен хотя бы в одной из меток; пусто или 0 — уверен |
| `comment` | свободно |

Обе метки, `claim` и `admit`, могут быть равны 1 одновременно.

## 5. Расчёт после разметки (зафиксирован до разметки)

- **Какие строки берутся.**
  - Строки без метки `claim` исключаются, их число сообщается.
  - Основной расчёт — на всех размеченных строках. Проверка — без строк с `unsure = 1`.
- **Для каждого класса r ∈ {1, 0}:**
  - p_r — доля `claim = 1` у автора в ячейке «детектор: да, r». Это **точность** детектора.
  - q_r — доля `claim = 1` у автора в ячейке «детектор: нет, r». Это доля пропущенных заявлений.
  - **Полнота** = N_да,r · p_r / (N_да,r · p_r + N_нет,r · q_r).
  - **Истинная доля заявлений** в классе = (N_да,r · p_r + N_нет,r · q_r) / (N_да,r + N_нет,r).
  - **Разность** истинных долей: решённые − нерешённые.
- **ДИ.** Стратифицированный бутстрэп: в каждой из 4 ячеек 1000 раз выборка с возвращением, seed 42; 95% —
  перцентильные. Повторы, где величина не определена (0/0), не учитываются, их число сообщается.
- **Для сравнения** — доли по детектору без поправки: 1877 / 5266 = 35.6% у решённых и 996 / 2598 = 38.3% у нерешённых.
- **Вывод одной фразой** — правило задано заранее:
  - ДИ разности содержит 0 → «вывод остаётся: различие долей заявлений после поправки не показано»;
  - ДИ выше 0 → «не остаётся: у решённых заявлений больше»;
  - ДИ ниже 0 → «не остаётся: у нерешённых заявлений больше».
- **admit — описательно.**
  - Истинная доля признаний по классам с теми же весами ячеек и бутстрэпом.
  - Точность и полнота детектора признаний — по тем же весам, если в выборку попали строки с `has_admit = 1`. Иначе —
    «не оценивается»: в популяции таких строк 12.
- **Описательно:** взвешенное согласие детектора и автора по `claim`.

## 6. Выходы

- `outputs/g0_human_sample.csv` (+ `outputs/g0_human_long/`, если понадобится) — для разметки.
- `outputs/g0_human_key.csv` — ключ; в репозиторий только после разметки.
- После разметки: `outputs/g0_human_results.json`, `reports/G0_HUMAN_CHECK.md`.

## 7. Процедура разметки (дополнение от 2026-11-10, до итогового анализа)

1. **Независимая разметка человеком.** Автор размечает id 1–30 сам, не видя предразметку модели. Поля и определения —
   раздел 4.
   - К моменту сравнения у автора были размечены id 1–39 (`g0_human_sample.xlsx` в корне репозитория; id 40 пуст).
   - Все 39 строк размечены до появления предразметки, поэтому сравнение ниже идёт на них.
2. **Предразметка моделью, вслепую.** Модель (Claude, Claude Code) размечает все 100 сообщений по смыслу текста, по
   правилам автора. Входные данные — только `id` и `final_message` из `outputs/g0_human_sample.csv`.
   - **Что модель не открывала:** ключ, прежнюю выборку `g0_manual_sample.csv`, выход детектора G0, `resolved`,
     модели, задачи, `run_id`. Регулярные выражения детектора G0 и его код не использовались.
   - **Результат:** `outputs/g0_ai_labels.csv` (`ai_claim`, `ai_admit`, `ai_unsure`, `ai_reason`). `ai_reason` —
     дословная цитата из сообщения, не больше 20 слов; для `ai_unsure = 1` добавлено короткое пояснение после « | ».
   - **Раскрытие.** Модель писала код выборки (раздел 3) и поэтому знает её устройство: 25 сообщений в каждой ячейке.
     При пробном запуске `analyze` на случайных метках (2026-11-08) модель видела сводку: в выборке нет строк с
     `has_admit = 1` детектора. Пометок детектора по отдельным `id` модель не видела.
3. **Согласие модели с человеком** на размеченных автором строках (id 1–39): доля совпадений и каппа Коэна по `claim`
   и `admit`, список расхождений — `outputs/g0_ai_agreement.json`. Пустая метка в размеченной строке считается 0.
4. **Проверка человеком** — файл `outputs/g0_human_sample.xlsx`.
   - Отмечены (`review_flag = 1`) и проверяются все случаи, где:
     - модель расходится с автором на id 1–40;
     - `ai_unsure = 1`;
     - `ai_admit = 1`;
     - `ai_claim = 0`.
   - Остальные строки проверяются выборочно; сколько строк и какие — записывается в отчёт.
5. **Окончательные метки — человека.** Автор переносит окончательные `claim`, `admit`, `unsure` (и `comment`) в
   `outputs/g0_human_sample.csv`. Итоговый анализ (раздел 5, `python -m src.g0_human_check analyze`) использует только
   эти метки; предразметка модели в расчёт не входит.
6. **В отчёте указываются:**
   - согласие модели с автором (п. 3);
   - сколько меток модели автор изменил при проверке — среди отмеченных и среди проверенных выборочно.

## 8. Уточнение: уровень заявления (2026-11-10, до возврата ключа)

Записано до того, как автор вернул ключ и проверил метки. Итоговый анализ к этому моменту не запускался. Где разделы
4–7 расходятся с этим разделом, действует раздел 8.

### 8.1. Причина

- На размеченных автором id 1–39 оба расхождения модели с автором по `claim` — пограничные формулировки:
  - id 38 — только отправка;
  - id 39 — «Looks solid… I'm satisfied» без утверждения результата.
- У модели 32 метки «не уверен», в основном того же типа: одобрение своей работы («The patch looks good»,
  «The patch is correct») без утверждения, что задача решена.
- Бинарная метка `claim` не различает такие случаи, поэтому вывод может зависеть от того, куда их отнести.

### 8.2. Уровень заявления `claim_level`

| уровень | значение | примеры |
|---|---|---|
| 2 | явное утверждение результата: задача решена, исправление работает, тесты проходят, работа готова | «The fix is complete and working», «All tests pass», «The issue is resolved» |
| 1 | одобрение своей работы без утверждения результата | «looks good», «patch is correct», «I'm satisfied» |
| 0 | нет заявления: описание изменений, только отправка, пустое сообщение | «I changed X in file Y», «Now let me submit» |

- **Где ставится.** В `outputs/g0_human_sample.csv` добавлен пустой столбец `claim_level`; его заполняет автор.
  Столбец `claim` оставлен для совместимости, анализ его не использует.
- **Строки без `claim_level`** исключаются из анализа заявлений; их число сообщается.
- **`admit` и `unsure`** — без изменений (раздел 4). В строке с заполненным `claim_level` пустые `admit` и `unsure`
  считаются 0.

### 8.3. Два варианта анализа

- **Варианты:**
  - **строгий:** заявление = 1 ⇔ `claim_level` = 2;
  - **широкий:** заявление = 1 ⇔ `claim_level` ≥ 1.
- **Что считается в каждом варианте:** точность, полнота, истинная доля заявлений по классам, разность долей «решённые
  − нерешённые» и её 95% ДИ — всё по разделу 5 (веса ячеек, стратифицированный бутстрэп, 1000, seed 42), плюс проверка
  без строк с `unsure = 1`.
- **Вывод одной фразой** (заменяет правило раздела 5):
  - в **обоих** вариантах ДИ разности включает 0 → «вывод устойчив: различие долей заявлений у решённых и нерешённых
    после поправки не показано ни в строгом, ни в широком варианте»;
  - в обоих вариантах ДИ не включает 0 и направление одинаково → «вывод не остаётся: у … заявлений больше (в обоих
    вариантах)»;
  - иначе → «вывод зависит от границы заявления (уровни 1 и 2)»; приводятся оба варианта.

### 8.4. Меры согласия

**Что вычисляется:** доля совпадений p_o, каппа Коэна и PABAK = 2·p_o − 1 (каппа с поправкой на распространённость и
смещение).

**Где:**
- детектор G0 против автора (раздел 5) — с весами ячеек, отдельно для строгого и широкого варианта и для `admit`;
- модель против окончательных меток автора (раздел 7) — по строкам выборки без весов, для строгого и широкого варианта
  (`ai_claim_level`) и для `admit`;
- модель против независимых меток автора (id 1–39, `outputs/g0_human_independent.csv`). Эти метки бинарные (`claim` без
  уровня), поэтому сравниваются с обоими вариантами `ai_claim_level` описательно. Пустая ячейка в этих строках
  считается 0 (раздел 7, п. 3).

**Ограничение:** каппа для `admit` не интерпретируется, если хотя бы у одной из сравниваемых сторон меньше 5
положительных меток; она приводится с этой пометкой, а опираться следует на p_o и PABAK.

### 8.5. Предразметка модели по новому правилу

- **Как сделано.** Модель добавила `ai_claim_level` той же слепой процедурой (раздел 7, п. 2): только `id` и текст
  сообщения. Столбец записан в `outputs/g0_ai_labels.csv` и в таблицу проверки `outputs/g0_review.xlsx` (бывший
  `outputs/g0_human_sample.xlsx`, переименован до начала проверки; в git не входит).
- **Правило.** Уровень — по формулировке. Утверждение результата с оговоркой («should resolve», «I believe the task is
  complete») — уровень 2, с `ai_unsure = 1`. Одобрение патча без результата — уровень 1. У всех 20 сообщений
  уровня 1 уже стояло `ai_unsure = 1`.
- **Итог:** уровень 2 — 68, уровень 1 — 20, уровень 0 — 12.
- **Изменения против бинарной `ai_claim`:** id 29, 34, 63 и 91 по смыслу — одобрение своей работы без результата
  (раньше `ai_claim = 0`). Теперь у них уровень 1, и в широком варианте они считаются заявлениями.
- **Флаги проверки** (`review_flag`) не менялись: все сообщения уровня 1 уже отмечены.

## 9. Отступление: окончательные метки — метки модели (2026-11-10, до итогового анализа)

Записано до запуска итогового анализа и до того, как кто-либо прочитал ключ.

**Решение автора.** Автор не проверяет метки: «разметь все сам и дай итог, у меня нет времени». Поэтому:

- **Окончательные метки — слепая предразметка модели** (раздел 7, п. 2; раздел 8.5): `claim_level` =
  `ai_claim_level`, `admit` = `ai_admit`, `unsure` = `ai_unsure` для всех 100 строк.
  - Метки перенесены в `outputs/g0_human_sample.csv`; в `comment` каждой строки стоит «метка модели, автор не
    проверял».
  - Предразметка закоммичена раньше (0baa698, d45abe4) и после этого не менялась.
  - Повторного прохода модели по своим меткам нет.
- **Следствие.** Это проверка детектора G0 **моделью, а не человеком**. Пункты 4 и 5 раздела 7 (проверка человеком,
  окончательные метки человека) не выполнены. Отчёт `reports/G0_HUMAN_CHECK.md` называет это прямо. Недостаток,
  отмеченный в документации («ручная» проверка, сделанная ИИ), для этой проверки остаётся.
- **Проверка с метками человека** (описательно). Тот же анализ (`analyze`), но на id 1–39 стоят независимые метки
  автора из `outputs/g0_human_independent.csv`, на id 40–100 — метки модели. Файл —
  `outputs/g0_labels_author_1_39.csv`.
  - Метки автора бинарные, поэтому `claim_level` = 2 при `claim` = 1 и 0 иначе. Значит, в этой проверке строгий и
    широкий варианты для id 1–39 совпадают.
  - Пустые `admit` и `unsure` считаются 0.
  - Выход — `outputs/g0_human_results_author_1_39.json`.
- **Ключ.** `outputs/g0_human_key.csv` коммитится вместе с результатами.
- **Порядок.** Метки фиксируются коммитом, затем запускается `analyze`.

## 10. Просмотр меток автором (2026-11-10, после анализа)

После анализа автор просмотрел все 100 сообщений вместе с метками модели и не нашёл ни одного случая, где поставил бы
другую метку. Окончательные метки — метки модели, полностью проверенные автором. Независимая разметка автора
(id 1–39) — согласие 94.9%, каппа 0.64, PABAK 0.90.

**Пояснения модели**, факты из файлов репозитория:
- Абзац выше — заявление автора, записанное с его слов. Модель не может его проверить. Метки и результаты после
  анализа не менялись, анализ не перезапускался.
- **Что сравнивалось.** 94.9% / 0.64 / 0.90 — согласие бинарной предразметки модели (`ai_claim`) с независимыми
  бинарными метками автора на id 1–39. С уровнями раздела 8 (`ai_claim_level`) согласие такое:
  - строгий вариант — 79.5% / 0.35 / 0.59;
  - широкий вариант — 89.7% / −0.04 / 0.79.

  Источник — `outputs/g0_ai_agreement.json`.
- **Расхождения.** В независимой разметке автор ставил другие метки, чем модель, на id 38 и 39 (`claim`) и на id 28 и
  34 (`admit`) — раздел 7, `outputs/g0_human_independent.csv`.
