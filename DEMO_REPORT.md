# DEMO_REPORT — демонстрационный Colab-ноутбук

## 1. Инвентаризация

1. **Сырые траектории.** Публичный бакет `swe-bench-submissions`, `bash-only/<прогон>/trajs/<задача>/<задача>.traj.json` — JSON с полем `messages` (сообщения system / user / assistant / tool / exit) и `info` (exit_status, версия, конфигурация); 16 прогонов × 500 задач. Полный набор (≈ 7.5 ГиБ по замеру при подготовке E0) скачивался и разбирался на Kaggle (ядро diss-e0); локально лежат 355 сырых траекторий с их `report.json` (198 МБ, `data/raw/swebench_bashonly/`) и весь разобранный набор `data/interim/swebench_bashonly/trajectories.jsonl.gz` (180 МБ, 7975 траекторий в схеме E0).
2. **Метки.** `bash-only/<прогон>/logs/<задача>/report.json` (поле `resolved`, плоский или вложенный формат); читает `read_label` адаптера, сопоставление — по папке прогона и instance_id. В разобранных траекториях и `outputs/traj_index.csv` хранится `label` (1 = провал); здесь `resolved = 1 − label`.
3. **Код.** Разбор на шаги — `src/adapters/swebench_bashonly.parse_trajectory` (assistant / tool / user, выполненные команды в `tool_calls`); разметка шагов — `src/g0_false_success.classify_segment` (события edit / verify), `src/e5_claims.command_events` (+ цель правки); фазы и признаки — `src/e5_claims.process_record` (E5), новые признаки — `src/e6_refine.block1_record` (E6); заявление об успехе — `src/g0_false_success` (`clean_nl`, `pick_final`, `match_any` с `config/claim_patterns.txt`).
4. **Поля прогона.** model_id, model_family, agent_id (версия mini-SWE-agent), meta.exit_status (Submitted: 7864, LimitsExceeded: 108, RetryError: 3), число шагов, meta.trajectory_format, meta.reasoning_sources. Отдельного поля «репозиторий» нет — выведено из instance_id.
5. **Признаки `M_struct+len` (E5).** В коде два списка: `LEN` = n_steps, seg_len_steps, seg_len_sent, n_edits и `STRUCT` = 17 структурных (has_any_verification, n_verifications, verif_after_last_edit, n_verif_after_last_edit, verified_before_first_edit, n_steps_after_last_edit, share_edit, share_verify, share_other, n_transitions, phase_bigram_entropy, share_before_first_edit, repeat_ratio, distinct_cmd_ratio, nonzero_rc_share, n_files_edited, n_file_switches); итого 21. **Разделения на «процессные» и «артефактные» в коде нет.** Все 21 считаются по процессу — шагам, командам, выводам среды и тексту рассуждений; ни один не использует артефакты (отправленный патч, результаты тестов): адаптер отбрасывает сообщение с сабмитом, эталонный патч нигде не читается. Поэтому «только процессные» = все 21.
6. **Расхождение с README.** README описывает четыре фазы (локализация, правка, верификация, прочее); в коде фаз три — edit / verify / other; демо использует разметку кода.
7. **Перенос кода.** Разметка фаз вынесена в `demo_lib/phases.py` дословным копированием функций (автоматически, по исходникам), признаки — `demo_lib/features.py` (логика `process_record` на пошаговых данных). Проверка на 100 случайных прогонах (seed 42): максимальное расхождение 0.0e+00, прогонов с иной разметкой фаз 0; на всех 7975 прогонах — 0.0e+00 и 0.

## 7. Что не сделано или упрощено

- **`final_message`** восстановлено из разобранных траекторий функциями G0 (`clean_nl`, `pick_final`): сверка с результатом G0 на всех 7975 прогонах — расхождений в заявлении 0, в номере финального шага 0, в длине текста 2 (`claim_success` при этом взят из G0 без пересчёта).
- **Доступ.** Репозиторий `Kiruha667/diss` на момент проверки публичный (GitHub: visibility PUBLIC; файлы релиза
  и `raw.githubusercontent.com` отдаются без входа, HTTP 200), поэтому кнопка «Open in Colab» и скачивание работают
  по ссылке. Если репозиторий снова закрыть, ноутбук остановится на загрузке с явной ошибкой.
- **На самом Colab ноутбук не запускался** (нет доступа из этой среды). Проверка — `jupyter nbconvert --execute` в
  чистом окружении Python 3.12 (pandas 3.0.6, numpy 2.5.4, pyarrow 26.0.0, scikit-learn 1.9.1) со скачиванием из
  релиза GitHub и сверкой SHA256. Время в Colab не измерено; скачивание там, как правило, намного быстрее, чем по
  каналу автора.
- **Скачивание с GitHub с этой машины нестабильно.** Из четырёх прогонов со скачиванием из релиза: первые два
  оборвались на загрузке (после них в ноутбук добавлены таймаут и три попытки на файл), третий прошёл (127 с, числа
  совпали с локальными), четвёртый не уложился в лимит ячейки 900 с — канал упал примерно до 37 КБ/с. Поэтому
  сохранённая версия с выводами (`notebooks/demo.ipynb`) выполнена с локального HTTP-сервера, раздающего те же
  файлы (SHA256 сверяются); исходный код ноутбука при этом тот же, что открывается в Colab.
- **Закреплена только версия scikit-learn** (1.9.1, от неё зависят коэффициенты логистической регрессии).
  numpy, pandas, pyarrow, scipy, matplotlib берутся из рантайма Colab (версии печатаются в ноутбуке): их
  переустановка в Colab требует перезапуска рантайма и ломает «Run all». scikit-learn 1.9.1 требует numpy ≥ 1.24.1,
  scipy ≥ 1.10, Python ≥ 3.11.
- **В `steps.parquet` четыре колонки сверх заданных** — `commands` (полный текст команд), `n_outputs`,
  `n_nonzero_rc`, `n_sent`. Без них `score_trajectory` не может точно пересчитать признаки: усечение команд до 300
  символов теряет тела heredoc (правки и `assert`), а `seg_len_sent` считается по полному тексту рассуждения.
  `n_sent` посчитан заранее сегментацией E1 (blingfire), потому что полный текст рассуждений в датасет не входит.
- **`returncode`**: адаптер E0 хранит только ненулевые коды; для шага с выводом и без ненулевого кода записан 0
  (в локально доступных сырых логах код возврата есть у каждого вывода). Для шагов с несколькими командами — первый
  ненулевой код.
- **`repo`** выведен из instance_id (`owner__repo-N`): отдельного поля в данных нет.
- **Модель `M_struct+len`** — 21 признак E5, как в задании (с дублем `n_steps_after_last_edit` и слабыми признаками),
  а не уточнённый набор E6.
- **AUROC внутри задач**: ничьи в паре считаются за 1/2. В таблицу добавлен столбец «AUROC, усреднённый по фолдам» —
  для сверки с объединённым out-of-fold AUROC, который требует задание.
- **Пример «ложное заявление»** модель оценивает низким риском (см. раздел 9 ноутбука) — показано как есть, без
  подбора более удачного примера.
