## 1. Тема и постановка

**Тема (утверждена):** Разработка модели оценки достоверности выполнения задач LLM-агентами на основе анализа структуры траекторий выполнения.
*Development of a Model for Assessing the Veracity of Task Completion by LLM Agents Based on the Analysis of Execution Trajectory Structure.*

- **Автор:** Селиванкин Кирилл Дмитриевич, AAI-2601M (научно-педагогическая магистратура, Applied Artificial Intelligence), Astana IT University.
- **Руководитель:** Assel Yerbolova, PhD, Assistant Professor. Не специалист в ИИ/LLM: материалы для неё нужны наглядные. Оценка руководителя по итоговым числам (AUROC 0.685, precision@10% 0.656): «мало» — нужна аргументация через сравнение с литературой.
- **Репозиторий:** github.com/Kiruha667/diss (публичный).

**Рабочее определение.** Агент завершает работу отправкой результата (патча) и тем самым заявляет, что задача выполнена. *Достоверность выполнения* — соответствие этого заявления фактическому исходу, проверенному скрытыми тестами бенчмарка, недоступными агенту. Модель по траектории (последовательности действий агента) оценивает вероятность того, что сданный результат не решает задачу, и ранжирует результаты для выборочной проверки человеком. Эталонный патч и скрытые тесты как вход не используются.

**Популяция:** только прогоны с отправкой результата. Прогоны без отправки (обрыв по лимиту, ошибка) исключаются: они тривиально провальные и завышают AUROC.

**Объект исследования** — процесс выполнения задач разработки ПО LLM-агентами. **Предмет** — связь структуры траектории выполнения с достоверностью сданного результата.

**История постановки:**

| Итерация | Замысел | Итог |
|---|---|---|
| 1 | Ранний прогноз провала по хаотичности семантических траекторий | Отрицательный: Δ AUROC 0.014 [−0.004; 0.031] |
| 2 | Достоверность *утверждений* агента об успехе (подвыборка 2 877 с явным заявлением) | 0.684; тема изменена руководителем |
| 3 | Достоверность *выполнения* (все прогоны с отправкой) | Текущая |

## 3. Методический протокол

- Логистическая регрессия, L2, StandardScaler, без подбора гиперпараметров — сравниваются признаки, а не алгоритмы.
- `GroupKFold(5)` по `task_id`, предсказания out-of-fold.
- Кластерный бутстрэп по задачам или единицам, 1000 итераций, seed 42.
- AUROC общий и **внутри задачи** (пары из одной задачи); на повторах — **внутри единицы** (одна настройка × одна задача).
- Перестановочные тесты внутри единиц; поправки Холма/Бонферрони там, где записаны в протоколе.
- **Протокол с критериями коммитится до расчётов** (проверяется по времени коммитов). Отступления и исследовательские анализы помечаются явно.
- Ручные проверки разметки — человеком (раньше часть проверок делал ИИ — это ошибка, см. раздел 10).

Признаки `S` (структура, 21) — `demo_lib/features.py`: наличие и число проверок, проверка после последней правки, доли фаз, биграммы/триграммы фаз, энтропия переходов, длина. Разных признаков 20: `seg_len_steps` и `n_steps_after_last_edit` совпадают (рецензия, С2). Правило «verify» узкое (запуск тестов проекта), «edit» широкое (включает создание своих тестовых скриптов) — в тексте разделять «запуск тестов проекта» и «проверку» (рецензия, С8). Фазы `edit / verify / other` по командам; признаки по отдельным командам, фаза шага — по главной команде. Ограничения правил: `python -m django test` не считается проверкой; скрипт с `.write(` считается правкой.

Блок E13: `P` — признаки диффа модели (не эталона): число файлов, добавленные/удалённые строки, правка тестов, файлы вне пакета, новые файлы; источник — `logs/<task>/patch.diff` из бакета.

Блоки E7: `M` — идентичность связки (one-hot 16); `T` — TF-IDF описания задачи + repo; `A` — TF-IDF финального сообщения; `R` — TF-IDF рассуждений. E10: `O` — исходы собственных проверок агента (19 признаков). E12: `T2` — эмбеддинг описания задачи (all-MiniLM-L6-v2, PCA 32) + repo.

## 11. Рабочий процесс

- Эксперименты выполняет Claude Code (возможно, также Codex) по спецификациям `.md`; результаты — через GitHub. Один агент на репозиторий одновременно.
- Протокол с критериями — коммит до расчётов; при оценке результатов сверяется время коммитов.
- Ключи API — только в переменных окружения; перед коммитом проверка на ключи.
- Автор работает полный день единственным техническим специалистом; время и бюджет ограничены; цель — надёжная защита.
- Стиль общения: жёсткий, без воды, TL;DR в начале, затем подробности; без эмодзи; без вопросов и предложений в конце; объяснять смысл чисел, а не только значения.
