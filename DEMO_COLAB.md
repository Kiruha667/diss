# DEMO_COLAB.md — демонстрационный Colab-ноутбук

## Цель

Один ноутбук `notebooks/demo.ipynb`, который руководитель открывает в Google Colab
по ссылке и выполняет целиком («Runtime → Run all») на чистом рантайме.
Ноутбук показывает: как устроен датасет, несколько реальных траекторий,
как из траектории получаются признаки, как модель обучается и оценивается,
и как модель выдаёт риск для отдельной траектории.

Тема работы: «Разработка модели оценки достоверности выполнения задач
LLM-агентами на основе анализа структуры траекторий выполнения».
Достоверность выполнения = агент отправил результат (submit), и скрытые тесты
SWE-bench подтверждают, что задача решена.

## Жёсткие ограничения

- Полное выполнение на чистом Colab-рантайме не дольше 3 минут.
- Без API-ключей, без вызовов LLM, без Docker, без доступа к приватным ресурсам.
- `seed = 42` везде, где есть случайность. Повторный запуск даёт те же числа.
- Ничего не выдумывать. Если нужного поля нет в данных — явно написать об этом
  в отчёте и в ноутбуке, а не подставлять заглушку.
- Не изменять существующие результаты экспериментов (`outputs/` и т. п.).
  Новые файлы — только в `data/demo/`, `notebooks/`, и отчёт в корне.
- Текст markdown-ячеек — на русском, коротко и по сути.
  Комментарии в коде — на английском.

## Шаг 1. Подготовка данных

Создай две таблицы.

### `data/demo/runs.parquet` — одна строка на прогон

Обязательные колонки (названия признаков сохрани как в существующем коде):

| Колонка | Тип | Смысл |
|---|---|---|
| `run_id` | str | уникальный id прогона |
| `task_id` | str | id задачи SWE-bench |
| `repo` | str | репозиторий задачи |
| `model` | str | LLM агента |
| `model_family` | str | семейство модели |
| `agent_version` | str | версия mini-SWE-agent |
| `n_steps` | int | число шагов |
| `exit_status` | str | чем закончился прогон |
| `submitted` | int 0/1 | была ли отправка результата |
| `claim_success` | int 0/1 | текстовое заявление об успехе (детектор G0) |
| `final_message` | str | финальное сообщение агента, до 1000 символов |
| `resolved` | int 0/1 | метка: прошли ли скрытые тесты |
| `phase_seq` | str | последовательность фаз одной строкой, коды через пробел |
| признаки | float | все признаки модели `M_struct+len` |

### `data/demo/steps.parquet` — одна строка на шаг

| Колонка | Тип | Смысл |
|---|---|---|
| `run_id` | str | к какому прогону |
| `step_idx` | int | номер шага с 0 |
| `thought` | str | рассуждение, до 500 символов |
| `command` | str | команда, до 300 символов |
| `output` | str | вывод среды, до 300 символов |
| `returncode` | int или null | код возврата, если извлекается |
| `phase` | str | фаза шага |

Коды фаз для `phase_seq` и легенду к ним возьми из существующей разметки
и опиши в карточке датасета.

### Хранение

- Если `runs.parquet` меньше 50 МБ — коммит в репозиторий.
- `steps.parquet` — в GitHub Release `demo-data-v1` репозитория `Kiruha667/diss`.
  Если файл больше 2 ГБ — сократи `thought`/`output` сильнее и сообщи об этом.
- Посчитай SHA256 обоих файлов. Ноутбук после скачивания сверяет хеши.

### `data/demo/DATASET_CARD.md`

Источник данных, ревизия или дата снапшота, SHA256, число строк в каждой таблице,
описание каждой колонки, легенда фаз, правило определения `submitted`,
известные ограничения (детектор заявлений на регулярных выражениях,
различие формата логов v1.x и v2.x).

## Шаг 2. Отбор примеров для показа

Отбор детерминированный (seed 42). Среди подходящих предпочитай прогоны
длиной 15–40 шагов — их можно прочитать целиком. Нужны:

1. **Пара внутри одной задачи:** одна задача, два прогона разных моделей,
   один `resolved=1`, другой `resolved=0`, оба `submitted=1`.
2. **Ложное заявление:** `submitted=1`, `claim_success=1`, `resolved=0`.
3. **Достоверное выполнение с проверкой:** `submitted=1`, `resolved=1`,
   в траектории есть хотя бы одна фаза проверки.
4. **Обрыв без отправки:** `submitted=0`. Нужен, чтобы показать,
   почему такие прогоны исключены из популяции.

Сохрани выбранные `run_id` в `data/demo/examples.json` с пометкой типа примера.

## Шаг 3. Структура ноутбука

Каждый раздел начинается markdown-ячейкой: 2–4 предложения, что показываем и зачем.

1. **Установка и загрузка.** Одна ячейка `pip install` с закреплёнными версиями;
   скачивание `runs.parquet`, `steps.parquet`, `examples.json` по прямым ссылкам;
   сверка SHA256.
2. **Обзор датасета.** `runs.shape`, `runs.dtypes`, `runs.head()`;
   доля `resolved`; число задач; число моделей; таблица «модель → число прогонов,
   доля решённых»; распределение `exit_status`; число задач, где есть и решённые,
   и нерешённые прогоны.
3. **Популяция.** Фильтр `submitted == 1`. Вывести, сколько прогонов исключено
   и почему. Все дальнейшие расчёты — только на этой популяции.
4. **Примеры траекторий.** Для каждого примера из `examples.json`:
   метаданные (задача, модель, число шагов, `claim_success`, `resolved`);
   `phase_seq` с легендой; таблица шагов (`step_idx`, `phase`, `command`,
   первые 150 символов `output`); `final_message`.
   Пару внутри задачи показать рядом: две последовательности фаз друг под другом.
5. **От траектории к признакам.** Для одного примера вызвать функцию извлечения
   признаков и показать получившийся вектор признаков с короткими пояснениями.
6. **Обучение и оценка.**
   - Модели: `M_len` (только длина) и `M_struct+len` (признаки E5, только процессные).
   - `LogisticRegression` с L2, `StandardScaler`, без подбора гиперпараметров.
   - `GroupKFold(n_splits=5)` по `task_id`, предсказания out-of-fold.
   - AUROC по всей популяции с 95% интервалом: кластерный бутстрэп по задачам,
     1000 итераций, seed 42. Также интервал разности `M_struct+len − M_len`.
   - AUROC внутри задач: все пары «нерешённый — решённый» из одной задачи,
     объединённые по всем задачам; доля пар, где нерешённый получил больший риск.
     Указать число задач и пар.
   - Одна столбчатая диаграмма: четыре AUROC (две модели × два режима) с интервалами.
7. **Практическая полезность.** precision@k и lift@k для бюджетов 5%, 10%, 20%
   по `M_len` и по `M_struct+len` в одной таблице.
8. **Ранжирование.** Топ-10 прогонов с наибольшим риском (out-of-fold):
   задача, модель, риск, `resolved`.
9. **Оценка одной траектории.** Функция `score_trajectory(steps_df) -> float`:
   принимает шаги одного прогона, размечает фазы, считает признаки, возвращает
   риск. Модель для демонстрации обучается на всех задачах, кроме задачи примера.
   Вызвать на каждом примере из раздела 4 и показать риск рядом с истинной меткой.
10. **Ограничения.** Пять пунктов: только SWE-bench и один каркас; метка — скрытые
    тесты бенчмарка; детектор заявлений на регулярных выражениях; признаки
    могут частично отражать идентичность модели; числа отличаются от прежних,
    посчитанных на подвыборке 2877 траекторий с заявлением.
